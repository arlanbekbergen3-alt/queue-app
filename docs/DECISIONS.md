# Решения, принятые без участия владельца

Формат: проблема, варианты, выбор, минусы. Всё это нужно подтвердить или изменить.

## 1. Порядок очереди: поле `sort_order`

- **Проблема.** `promote` менял `ticket` (сначала `min-1`, потом ротация), а номер должен быть постоянным.
- **Варианты.** (а) оставить ротацию номеров; (б) поле `sort_order`, `ticket` неизменен; (в) дробные позиции (`float`/`numeric`) между соседями.
- **Выбор.** (б). `sort_order` заполняется при входе значением `ticket`. `promote` ставит `sort_order = sort_order первого ожидающего - 1`. `requeue` берёт новое число из того же счётчика `next_ticket`, значит попадает строго в конец и не совпадает с записями, которые войдут позже. В БД есть частичный уникальный индекс `(session_id, sort_order) WHERE status='waiting'`: ошибка порядка превращается в ошибку БД, а не в тихую неправильную очередь.
- **Минусы.** (1) `requeue` расходует число из счётчика, поэтому в номерах следующих студентов появляется «дырка» (проверено тестом: номера уникальны, но не обязательно подряд). (2) `sort_order` у продвинутых уходит в отрицательные значения, это внутреннее поле, студент его не видит. (3) Миграция копирует `ticket` в `sort_order` как есть: у старых записей, где `promote` уже сделал номер 0 или -1, эти номера не исправляются (данных только локальных, проверено запуском на копии с такими строками).

## 2. e2e-тесты: как запускать сервер

- **Проблема.** Нужен настоящий браузер против настоящего сервера, но не против рабочей БД.
- **Варианты.** (а) ASGI-приложение в том же процессе (браузеру нужен реальный порт, не подходит); (б) подпроцесс `uvicorn` на свободном порту с отдельной БД `queue_e2e`; (в) полный `docker compose` на каждый прогон.
- **Выбор.** (б): БД создаётся заново, схема накатывается `alembic upgrade head` (заодно проверяются миграции), после тестов БД удаляется.
- **Минусы.** Тесты ждут реальный опрос страницы (5-6 с), весь набор идёт около 30-35 с. Нужны установленные Playwright и Chromium (`python -m playwright install chromium`); без них тесты пропускаются (`importorskip` пропускает только отсутствие пакета, не отсутствие браузера, поэтому при пакете без браузера они упадут).

## 3. Русские сообщения об ошибках на странице студента

- **Проблема.** API отдаёт английские `detail`, студент видел «Session is closed» (найдено e2e).
- **Варианты.** (а) перевести тексты в API (сломает контракт и тесты); (б) словарь соответствий в `static/index.html`.
- **Выбор.** (б), API не менялся. Неизвестный `detail` показывается как есть.
- **Минусы.** Два места, которые нужно держать согласованными вручную. Страница преподавателя пока показывает `detail` как есть (английский), проверено только для студента.

## 4. SSE: рассылка из памяти процесса

- **Проблема.** 300 студентов с SSE не должны дать больше нагрузки на БД, чем опрос раз в 5 с (около 60 запросов/с).
- **Варианты.** (а) на каждое изменение каждый поток сам читает свой вид из БД (300 запросов на изменение, при 5 входах в секунду это 1500 запросов/с, хуже опроса); (б) один снимок очереди сессии, который перезагружается не чаще раза в `SSE_COALESCE_SECONDS` (0,3 с), а вид каждого студента считается из снимка в памяти; (в) Redis pub/sub.
- **Выбор.** (б). Изменение (`notify_changed` после `commit`) помечает сессию «грязной», один фоновый цикл на сессию делает 2 коротких запроса. Потоки соединение БД не держат (проверено тестом на `engine.pool.checkedout() == 0`).
- **Транспорт.** Браузерный `EventSource` не умеет заголовки, а токен записи нельзя класть в URL (попадёт в логи). Поэтому страницы читают поток через `fetch` + `ReadableStream`, заголовок `X-Entry-Token` / `Authorization` остаётся как в остальных запросах.
- **Минусы и отложенное решение.** Хаб живёт в памяти одного процесса. Если запустить несколько процессов (`--workers N`) или несколько контейнеров, изменение, сделанное в одном процессе, не дойдёт до потоков другого (опрос раз в 60 с у студента и 30 с у преподавателя при живом потоке всё равно исправит картину, но медленно). **Отложено:** для нескольких процессов нужен Redis pub/sub или `LISTEN/NOTIFY` в PostgreSQL (из `notify_changed` отправлять код сессии, подписчики в каждом процессе вызывают `hub.publish`). Сейчас в проекте один процесс, и это не реализовано.
- **Прочее.** Отключение клиента сервер замечает при следующей отправке (ASGI 2.4), то есть не позже интервала heartbeat (15 с). Студенту, чья запись завершена (`done`/`left`), приходит последнее состояние и событие `end`. Тест HTTP-уровня через живой сервер добавлен после шага 6 (нужны метрики).

## 5. Лимиты частоты: значения по умолчанию и NAT колледжа

- **Проблема.** Студенты могут сидеть за одним внешним IP (Wi-Fi колледжа с NAT, **предположение**: не проверял). Жёсткий лимит на IP заблокирует всю группу.
- **Варианты.** (а) жёсткие лимиты на IP; (б) только лимит на токен записи; (в) щедрые лимиты на IP как защита от скриптов и строгий лимит там, где работает один человек (вход преподавателя), плюс лимит на токен записи.
- **Выбор.** (в). По умолчанию: все запросы с IP 6000/мин, `join` с IP 600/мин (300 студентов за 60 с проходят), `login/register` 20/мин с IP, запросы по токену записи 120/мин (клиент делает около 12/мин). Всё настраивается переменными `RATE_LIMIT_*`, `RATE_LIMIT_ENABLED=false` отключает.
- **Минусы.** (1) Окно фиксированное, на границе минуты возможен двойной всплеск. (2) Счётчики в памяти одного процесса (как SSE-хаб); для нескольких процессов нужен общий счётчик (Redis). (3) За reverse proxy видно IP прокси, если не включить `--proxy-headers` и `FORWARDED_ALLOW_IPS` у uvicorn (описано в `docs/DEPLOY.md`). (4) Студент, который генерирует новые токены, обходит защиту «по токену», его ограничивают лимит `join` с IP и `MAX_QUEUE_SIZE`.

## 6. Общий лимит одновременных запросов и таймаут пула

- **Проблема.** Перегрузка давала ожидание до 10 с и 503 только после таймаута пула.
- **Варианты.** Лимит 100 запросов и таймаут 3 с (первая версия); лимит 400 и таймаут 3 с; лимит 400 и таймаут 10 с; ничего не менять.
- **Измерение (сценарий «залп», 300 входов за 5 секунд, по одному прогону на вариант, машина шумная).** Базовый код: 0% ошибок, p95 `join` 2632 мс. Лимит 100 и таймаут 3 с: **23% ошибок** (69 входов получили 503, остальные ошибки это 404 на `/me` у студентов, чей вход не прошёл). Лимит 400 и таймаут 3 с: 0,98% ошибок, p95 `join` 2019 мс. Лимит 400 и таймаут 10 с: 0,35% ошибок (один 503, причина не установлена: максимальное время входа было 3,2 с), p95 `join` 1714 мс.
- **Выбор.** `MAX_CONCURRENT_REQUESTS=400` (больше размера группы и SSE не считается) и `DB_POOL_TIMEOUT_SECONDS=10` (как было). Быстрый 503 теперь срабатывает при переполнении по числу запросов, а ожидание соединения остаётся прежним.
- **Минусы.** Это означает, что «быстрый отказ вместо 10 секунд ожидания соединения» из пожелания выполнен только частично: при исчерпании пула ожидание по-прежнему до 10 с. Выбор сделан по одному прогону на вариант, разброс между повторами мог бы изменить вывод; один оставшийся отказ не объяснён. Лимит считается по процессу.

## 7. Лимит записей и гонка `MAX_QUEUE_SIZE`

- **Проблема.** Проверка размера очереди стояла до блокировки: 12 параллельных входов при лимите 5 принимались все (проверено запуском). Дополнительно число записей за сессию (с вышедшими и сдавшими) не ограничивалось.
- **Выбор.** Быстрая проверка оставлена до блокировки, повторная идёт после `allocate_ticket`, когда строка сессии заблокирована. Добавлены `MAX_ENTRIES_PER_SESSION` (1000 по умолчанию) и ответ 409 `Session is full`.
- **Минусы.** Дополнительный запрос `count` на каждый вход (индекс по `session_id` есть). Значение 1000 не обосновано измерением.

## 8. Поле «группа» и связь с названием

- **Проблема.** Нужно показывать группу в интерфейсах; отдельной сущности «группа» в проекте нет.
- **Варианты.** (а) отдельная таблица `groups` и связь; (б) необязательная строка у сессии.
- **Выбор.** (б), столбец `queue_sessions.group_name VARCHAR(60) NULL`, в API поле `group`. Пустая строка превращается в `NULL`, управляющие символы запрещены.
- **Минусы.** Нет списка групп и фильтрации, опечатки в названии не отлавливаются; группы одного названия у разных преподавателей независимы. Для задач «все сессии группы» понадобится отдельная таблица.

## 9. Эксплуатация: `/health`, `/ready`, метрики

- **Проблема.** `/health` ходил в БД, поэтому при перегрузке пула healthcheck ронял контейнер, хотя процесс жив.
- **Выбор.** `/health` без БД (жив ли процесс), `/ready` с `SELECT` из `alembic_version` и сверкой с последней миграцией (готов ли принимать трафик), `/metrics` в текстовом формате Prometheus без зависимостей: счётчики запросов по классам статусов, гистограмма времени, отказы по лимитам, число SSE-подключений, занятые соединения пула. Для 300 пользователей этого достаточно, чтобы увидеть перегрузку; внешний Prometheus/Grafana не настраивался.
- **Минусы.** Метрики в памяти одного процесса и обнуляются при перезапуске; нет меток по маршрутам (сознательно, чтобы не плодить ряды). `/metrics` по умолчанию без авторизации: в `docs/DEPLOY.md` указано закрыть его на reverse proxy или задать `METRICS_TOKEN`.
- **Изменение поведения API.** Тело любой ошибки теперь `{detail, code, request_id}`; поле `detail` осталось строкой, добавлены `code` (машинный) и `request_id`. Старые клиенты, читающие только `detail`, продолжают работать, кроме ошибок 422, где раньше `detail` был списком, а теперь строка, а список ушёл в `errors`.

## 10. Автозакрытие забытых сессий

- **Проблема.** Преподаватель забыл закрыть сессию, она остаётся открытой, студенты могут вставать в очередь.
- **Выбор.** Фоновая задача раз в `SESSION_REAPER_INTERVAL_SECONDS` (60) закрывает открытые сессии, у которых нет активности (вход, вызов, завершение) дольше `SESSION_AUTO_CLOSE_HOURS` (по умолчанию 6; `0` отключает). Активность считается по меткам времени записей, отдельного столбца нет (схема не менялась). Ждущие записи при закрытии не меняются, как и при ручном закрытии.
- **Минусы.** Значение 6 часов не обосновано измерением. Один и тот же `UPDATE` выполняет каждый процесс (безопасно, но лишний запрос). Задача живёт в процессе приложения, отдельного планировщика нет.

## 11. Валидация настроек при старте

- **Выбор.** `Settings` проверяет диапазоны, схему `DATABASE_URL`, длину секретов (JWT-ключ от 32 символов, код приглашения от 8) и отвергает значения-заглушки `change-me...`. Приложение не стартует с ошибкой, где указано, какое поле неверно.
- **Минусы.** Значения из `.env.example` (`change-me`) специально не проходят проверку: перед первым запуском нужно подставить свои. Это сознательное неудобство.

## 12. Что считается «до» в нагрузочных прогонах

- **Проблема.** Образ с кодом предыдущего этапа (оптимизации v2 до сегодняшних правок) пересобран, точного «до» нет.
- **Выбор.** Базой считается образ `queue_tmp_baseline:step1`: код после шага 1 (оптимизации v2, `sort_order`), до SSE, лимитов, нового middleware и формата ошибок. Это не код начала этапа 2 и тем более не первая версия (v0), измеренная раньше.
- **Минусы.** Различия между базой и новым кодом смешивают несколько изменений сразу (SSE-хаб, лимиты, pure-ASGI middleware, метрики, логирование, единый формат ошибок), по одному их вклад не измерен.

## 13. Dockerfile, compose и настройки доступа

- **Выбор.** Порты `postgres` и `web` в compose привязаны к `127.0.0.1` (наружу только через reverse proxy), `restart: unless-stopped`, время остановки 15 с, uvicorn с `--proxy-headers` и `--timeout-graceful-shutdown 10`, образ без dev-зависимостей, процесс не от root (`uid 1000`), healthcheck по `/health`. `.dockerignore` и `.gitignore` не пропускают `.env*` (кроме `.env.example`), ключи и `*.pem`.
- **Минусы.** Миграции выполняются при старте контейнера `web`: при нескольких репликах они будут конкурировать (процесс сейчас один). Публикация порта БД на `127.0.0.1` удобна для разработки, но на сервере её можно убрать совсем.

## 14. Очередь входов одной сессии в памяти и вставка одним запросом

- **Проблема.** В SSE-залпе (`ssesalvo-new-1`) p95 входа был 31 с, 38 отказов `join` и 11 отказов потоков. Причина **предположительно** (не доказана): все входы ждут блокировку строки сессии, держа соединения пула, а открытие потоков, которым тоже нужны соединения, голодает.
- **Варианты.** (а) увеличить пул; (б) ждать блокировку в памяти (`asyncio.Lock` на код сессии), а в БД идти по одному; (в) оставить как есть.
- **Выбор.** (б), плюс лимит очереди и вставка одним `INSERT ... SELECT ... WHERE` (`insert_entry_if_room`), чтобы граница лимита не зависела от шлюза.
- **Проверено запуском:** тесты падают без шлюза (2 теста) и без `WHERE` (1 тест); весь набор проходит. **Не проверено:** что это устраняет деградацию залпа (серии на тихой машине запустит владелец, `LOADTEST.md`, «Что повторить»).
- **Минусы.** Шлюз живёт в памяти одного процесса (как SSE-хаб и лимиты); при нескольких процессах входы сериализует только блокировка БД, как раньше.

## 15. Протокол сдачи: критерии блокируются, вопросы со снимками (нужно подтвердить)

- **Проблема.** После первой сдачи правка критериев меняла бы смысл старых оценок.
- **Варианты.** (а) версионирование критериев; (б) запрет правки критериев после первой сдачи с понятной ошибкой; (в) свободная правка.
- **Выбор.** (б): добавление, правка и удаление критериев дают 409 `criteria_locked`. Вопросы правятся свободно: сдача хранит снимок текста и сложности (`submission_questions`). Работу с хотя бы одной сдачей удалить нельзя (409 `assignment_has_submissions`), сессии с работой нельзя менять работу после первой сдачи (409 `session_has_submissions`).
- **Минусы.** Опечатку в критерии после первой сдачи не исправить, нужна новая работа. Версионирование было бы гибче, но сложнее и неочевиднее для студентов.
- **Проверено запуском:** `test_criteria_are_locked_after_first_submission_and_snapshots_survive`; мутация (отключить запрет) роняет тест.

## 16. Журнал оценок неизменяем триггером БД (нужно подтвердить)

- **Выбор.** Таблица `audit_log` без внешних ключей, триггер запрещает `UPDATE` и `DELETE`, причина правки обязательна (`CHECK` и проверка схемы). Журнал пишут завершение и правка после завершения; черновики до завершения не журналируются.
- **Минусы.** Администратор БД может отключить триггер; нет цепочки хешей; оценки хранятся открытым текстом; бэкапы содержат оценки.
- **Проверено запуском:** прямой `UPDATE` и `DELETE` падают; цепочка «было → стало» не рвётся при 10 параллельных правках, мутация (убрать блокировку сессии) роняет тест.

## 17. Завершение сдачи закрывает запись; `done` при открытой сдаче запрещён (нужно подтвердить)

- **Проблема.** Нужна одна точка завершения, иначе запись может быть «сдана» без оценок.
- **Выбор.** `POST /submissions/{id}/complete` ставит оценки и переводит запись в `done` в одной транзакции под блокировкой сессии. Для сессий **с подключённой работой** `POST /entries/{id}/done` при открытой сдаче даёт 409 `submission_open`. Пропуск и выход студента отменяют открытую сдачу (`cancelled`); возврат и повторный вызов открывает ту же сдачу с теми же вопросами и записью `reopen` в журнале. Сессии без работы работают как раньше (проверено тестом).
- **Минусы.** Единственное изменение поведения существующего API, и оно касается только сессий с работой.

## 18. Случайный выбор вопросов (нужно подтвердить)

- **Выбор.** По умолчанию 3 вопроса на сдачу (настройка работы, 1..10). Зерно 128 бит из `secrets` и пул сохраняются, выбор `random.Random(seed).sample` без повторов; если в банке меньше вопросов, берутся все и в карточке пометка. Без баланса по сложности. Повторный вызов того же студента не пересчитывает выбор.
- **Минусы.** Преподаватель видит зерно и пул (для аудита). Выбор воспроизводится по сохранённому пулу, а не по текущему банку.

## 19. Пределы протокола (нужно подтвердить)

- До 50 работ на преподавателя, 200 вопросов в банке, 20 критериев, баллы критерия 1..100, 3000 токенов вывода модели и другие размеры. **Значения не обоснованы измерением.**
- Работа привязывается к сессии (одна работа на сессию), не к записи.

## 28. «Не готов, пропустите меня» и окно записи (нужно подтвердить)

- **Выбор.** Отметка хранится в записи студента (`entries.not_ready`, счётчик `not_ready_count`), номер талона и `sort_order` не меняются. Порядок вызова: сначала все «готовые» по `sort_order`, затем «не готовые» по `sort_order` (во всех местах: вызов следующего, позиция студента, список преподавателя, снимок SSE). Кнопка «Готов» снимает отметку, студент встаёт на место по своему номеру. Лимит отметок: `NOT_READY_MAX_PER_SESSION` (по умолчанию 2, 0-10, 0 выключает функцию); считаются отметки, а не время в состоянии «не готов», повторное нажатие при уже стоящей отметке ничего не тратит.
- **Преподаватель.** «Вперёд» снимает отметку и ставит студента первым среди всех ждущих; «Вернуть» после пропуска тоже сбрасывает отметку; пропуск работает как раньше. Счётчик виден у каждого студента («не готов», «×N»).
- **Окно записи.** Новое поле `queue_sessions.join_open` (по умолчанию открыто), `PUT /sessions/{code}/registration {"open": bool}`. При закрытой записи новый вход возвращает 409 `registration_closed` («Запись закрыта»); студент, уже стоящий в очереди, может повторно войти по своему токену и очередь не меняется. Закрытая сессия по-прежнему отвечает `session_closed`, и снова открыть запись в закрытой сессии нельзя.
- **`join_gate`.** Это процессная блокировка `asyncio.Lock` на код сессии, а не флаг «запись открыта», поэтому окно записи сделано полем в БД; `join_gate` оставлен как есть (сериализует вход внутри процесса). Проверка окна идёт под блокировкой строки сессии (`FOR UPDATE`), поэтому после ответа на закрытие ни один новый вход не проходит.
- **Блокировки.** «Не готов», «Готов», вызов следующего, закрытие записи и закрытие сессии берут блокировку строки сессии; тесты на гонки: 10 одновременных «не готов» от одного студента тратят одну отметку, чередование «не готов»/«готов» не превышает лимит, «не готов» против вызова следующего никогда не отдаёт вызов «не готовому» при готовом ждущем, закрытие записи против 12 входов даёт согласованную очередь.
- **Язык ошибок.** Тексты ошибок новых функций (этапы 28-32) пишутся в `detail` на русском, коды стабильны; страницы показывают текст по коду.
- **Минусы.** Отметка не снимается автоматически (студент, забывший нажать «Готов», остаётся в конце); лимит 2 выбран без данных. Каждый новый вход теперь берёт блокировку строки сессии до проверок (раньше блокировка возникала только при выдаче талона); нагрузка не перемерялась.

## 29. История студента и пересдачи (нужно подтвердить)

- **Связь сдач одного человека.** У студентов нет аккаунтов, поэтому добавлена таблица `students` (запись-личность) и `entries.student_id`. Ключ автоматической связи: (преподаватель, группа, нормализованное имя), где нормализация это NFKC, нижний регистр, `ё`→`е`, удаление всех пробелов; пустая группа это отдельное значение. «Иванов Иван» и «Иван Иванов», «Анна» и «Анна К.», разные группы и разные преподаватели **никогда** не связываются автоматически. Уникальность ключа обеспечивает частичный индекс `uq_students_auto_key` (где `auto_link`), создание записи идёт через `INSERT ... ON CONFLICT DO NOTHING`, поэтому параллельные входы под одним именем дают одну запись (тест на 6 параллельных входов).
- **Ручное объединение и разделение.** `POST /students/{id}/merge {into_student_id}`: записи объединяются (в источнике ставится `merged_into_id`, все сдачи переходят в целевую, прежние ссылки перенаправляются), поэтому и будущие входы под старым именем попадают в объединённую запись. Отменить объединение нельзя, но `POST /submissions/{id}/student {student_id|null}` переносит одну сдачу в другую запись или в новую (`auto_link=false`, автосвязь на неё не действует): так разделяют тёзок. Обе операции выполняются под блокировками строк (сначала работы по возрастанию id, затем записи студентов по возрастанию id), чтобы не было взаимных блокировок; встречные объединения A→B и B→A дают ровно один успех и один 409.
- **Номер попытки.** `submissions.attempt_number`: порядковый номер среди неотменённых сдач этой работы у этой записи по `started_at`. Отменённая сдача (студент вышел, сессия закрыта) попытку не занимает и в истории без номера. Номера пересчитываются при создании сдачи (под блокировкой работы), возврате пропущенного, объединении и переносе. Пропущенного и возвращённого студента вызывают с теми же вопросами и тем же номером.
- **Вопросы пересдачи.** `choose_question_ids(seed, pool, n, usage)`: вопросы группируются по числу прежних показов этому человеку (завершённые и идущие сдачи этой работы), берутся сначала не бывшие, затем наименее использованные, внутри группы случайно по зерну. Без истории выбор совпадает с прежним (`random.sample`), поэтому прежний тест воспроизводимости не менялся. Для аудита в сдачу пишется `selection_usage` (только у пересдач; видно преподавателю), по `seed`, `pool_question_ids` и `selection_usage` выбор повторяется (тест).
- **Что студент видит.** `GET /sessions/{code}/me/history` по токену своей записи. Чтобы тёзка не получил чужую историю, введя то же имя, студенту показываются только завершённые сдачи записей с тем же `device_hash` (браузер генерирует случайный ключ `queue-device` в localStorage и шлёт его при входе; хранится только хеш) и той же личностью. Без ключа (прежний клиент, закрытый localStorage) виден только итог текущей сдачи. Преподавателю история доступна через `GET /students` и `GET /students/{id}` (карточка по работам: сдачи, даты, баллы по критериям, итог, динамика в п.п. между завершёнными попытками, вопросы и сколько раз каждый выпадал); чужому преподавателю 404, без токена 401. Страницы: `/students` (преподаватель), блок «Ваши попытки» на странице студента (при двух и более попытках).
- **Аудит и аналитика.** Журнал не менялся и ничего не пишет при объединении или переносе (проверено тестом по числу строк); аналитика осталась по номеру талона и от 5 сдач.
- **Совместимость API.** Добавлены необязательные поля: `device_key` при входе, `attempt_number` в `SubmissionOut` и `MySubmissionOut` (тест точного формата `MySubmissionOut` обновлён), `selection_usage` в карточке сдачи.
- **Минусы.** Общий компьютер: если студент B введёт имя A в том же браузере, он увидит историю A (имя и устройство совпали). Тёзки в одной группе до ручного разделения делят одну запись и попытки. Перенос сдачи не меняет уже выбранные вопросы. Для существующих данных миграция создаёт записи студентов и номера попыток по тем же правилам.

## 30. Слабые места в аналитике (нужно подтвердить)

- **Что считается.** По завершённым сдачам: для каждого критерия средний процент от его максимума и доля сдач ниже 50% (`баллы * 2 < максимум`, ровно половина не провал); самые слабые критерии (до трёх) по возрастанию среднего, при равенстве по большей доле провалов, затем по названию; распределение итогов по десяти корзинам (100% попадает в последнюю); средний итог и доля итогов ниже половины.
- **Вопросы.** Баллов за отдельный вопрос в модели нет, поэтому вопрос оценивается по итогу тех сдач, где он выпал (каждый вопрос один раз на сдачу). Это косвенный показатель: на него влияют остальные вопросы той же сдачи. Вопрос показывается только если выпал не меньше `ANALYTICS_MIN_SUBMISSIONS` раз; показывается до пяти худших, остальные считаются в `hidden_questions`. Тексты берутся из снимка вопросов сдачи, поэтому удалённые из банка вопросы тоже учитываются.
- **Порог.** Минимум 5 сдач (настройка прежняя) проверяется для каждой выборки отдельно: все, первые попытки, пересдачи. Критерий, выставленный меньше порога раз, пропускается. При нехватке данных числа не отдаются, только пояснение. Если у работы нет критериев, процент от максимума посчитать нельзя: возвращается пояснение, а таблицы и распределение пусты.
- **Первые попытки и пересдачи.** Делятся по `attempt_number` (пересдача, если больше 1); на странице отдельные блоки показываются только когда есть пересдачи. Номер попытки опирается на связь студентов из п. 29, поэтому ошибочная связь тёзок искажает деление (исправляется ручным разделением).
- **Приватность.** В блоках нет имён, талонов и идентификаторов студентов (тест). Права те же: чужому преподавателю 404, без токена 401.
- **Совместимость.** Добавлены только новые поля ответа; прежние поля и их тексты не менялись. Страница показывает таблицы и полосы построением DOM без `innerHTML`.
- **Минусы.** Оценка вопроса по итогу сдач грубая и ложно «обвиняет» вопросы, которые часто попадались слабым студентам; корзины фиксированы по 10%; на выборках около 5 сдач разброс большой, это показано только пояснением.

## 31. Копирование работ и шаблоны (нужно подтвердить)

- **Что копируется.** `POST /assignments/{id}/copy {title?}` создаёт новую работу преподавателя: описание, число вопросов на сдачу, флаг тренировки, критерии (название, максимум, порядок) и банк вопросов (текст, сложность, тема, порядок). Не копируются сдачи, баллы, журнал изменений, сессии, черновики ИИ и связи со студентами; у копии `submissions_count = 0`, критерии не заблокированы. Копия получает новые идентификаторы и никак не связана с исходной: правка, удаление вопроса или удаление всей исходной работы копию не затрагивают (тест).
- **Название.** По умолчанию «<название> (копия)», при занятом имени «(копия 2)», «(копия 3)»; длинное название обрезается так, чтобы результат укладывался в 120 символов. Своё название принимается (пробелы по краям убираются); если оно занято, 409 `assignment_title_taken` «Работа с таким названием уже есть», пустое или длиннее 120 даёт 422.
- **Шаблон.** Поле `assignments.is_template` (по умолчанию false) включается в карточке работы («Использовать как шаблон»). `GET /assignment-templates` возвращает только шаблоны этого преподавателя, `POST /assignment-templates/{id}/create {title?}` создаёт работу из шаблона так же, как копия (шаблонность не наследуется). Шаблон не отдельная сущность, а пометка обычной работы: проще, но правка шаблона меняет то, из чего создаются новые работы.
- **Права.** Копировать можно только свою работу; чужая или несуществующая даёт 404 `assignment_not_found`, без токена 401. Общий банк предметной группы из п. 32 это единственный путь получить чужие материалы.
- **Лимиты и гонки.** Копия подчиняется `MAX_ASSIGNMENTS_PER_TEACHER` (409 `assignment_limit`, «Достигнут предел числа работ»); размеры банка и критериев не превышают исходные, которые уже ограничены `MAX_QUESTIONS_PER_ASSIGNMENT` и `MAX_CRITERIA_PER_ASSIGNMENT`. Копирование берёт консультативную блокировку на преподавателя (`pg_advisory_xact_lock`) и блокировку строки исходной работы, поэтому 8 параллельных копий дают 8 разных названий, а гонка за лимит даёт ровно допустимое число копий; копия во время удаления вопросов получает согласованный банк (тесты). Остальные операции работ эту блокировку не берут: параллельное обычное создание работы может занять название раньше, тогда копия вернёт 409.
- **Минусы.** Копия снимает состояние банка на момент блокировки, а не историю; нет массового копирования и копирования между преподавателями вне п. 32.

## 32. Общий банк предметной группы (нужно подтвердить)

- **Модель.** «Предметная группа» (`subject_spaces`): название, код приглашения, владелец; участники (`space_members`, владелец тоже участник); публикации (`space_publications` с критериями `space_publication_criteria` и вопросами `space_publication_questions`). Публикация это **снимок** критериев и банка вопросов (текст, сложность, тема, порядок) на момент публикации, без ссылки на исходную работу: дальнейшие правки автора в группу не попадают, а сама работа участникам недоступна.
- **Роли и операции.** Владелец создаёт группу, видит и может сменить код приглашения (`POST /spaces/{id}/invite`, старый код перестаёт работать), удаляет участников и группу. Остальные входят по коду (`POST /spaces/join`, регистр и пробелы не важны, повторный вход ничего не меняет). Участник публикует свою работу (`POST /spaces/{id}/publications`), смотрит материалы группы, копирует материал в свою новую работу (`POST /spaces/{id}/publications/{pid}/copy`) и может выйти. Снять публикацию с группы (`DELETE`) может только её автор; владелец чужие материалы не снимает, у него есть удаление участника и группы. Редактирования чужих материалов нет вообще: на публикации нет изменяющих методов (PATCH/PUT дают 405).
- **Атрибуция.** Копия получает в `assignments` три текстовых снимка: автор (имя пользователя), группа, название материала, и показывает их на странице работы. Это строки, а не ссылки, поэтому снятие публикации, выход автора или удаление группы копию не ломают: копии остаются у тех, кто их сделал (тесты). Копия называется как в п. 31 (по умолчанию «<название> (копия)», можно своё название), подчиняется `MAX_ASSIGNMENTS_PER_TEACHER` и не наследует флаг шаблона.
- **Что видно участникам.** Только критерии и вопросы опубликованных материалов, имена участников группы и авторов. Студенты, баллы, сдачи, журнал, аналитика, сессии и сами работы авторов недоступны: никаких новых путей к ним нет, а прежние проверяют владельца (тест: участник получает 404 по работе, сессии, аналитике, сдаче и журналу автора, а в ответах группы нет ни имён студентов, ни комментариев, ни идентификатора исходной работы). Не участнику группа неотличима от несуществующей (404 `space_not_found`, а не 403).
- **Выход и удаление.** При выходе участника или удалении его владельцем исчезают и его публикации (материал остаётся только пока автор в группе); уже сделанные копии не затрагиваются. Владелец выйти не может (`owner_cannot_leave`), только удалить группу; удаление каскадом убирает участников и публикации.
- **Лимиты (настройки).** `MAX_SPACES_OWNED=5` групп на владельца, `MAX_SPACES_JOINED=10` членств на преподавателя, `MAX_SPACE_MEMBERS=30`, `MAX_SPACE_PUBLICATIONS=100` материалов в группе, `MAX_PUBLICATIONS_PER_AUTHOR=20` на автора в группе; размер материала ограничен теми же `MAX_QUESTIONS_PER_ASSIGNMENT` и `MAX_CRITERIA_PER_ASSIGNMENT`, так как публикуется существующая работа. Пустая работа (ни критериев, ни вопросов) не публикуется (422 `publication_empty`). Ошибки возвращаются на русском с устойчивыми кодами (`space_limit`, `space_full`, `publication_limit` и др.).
- **Блокировки и гонки.** Создание и вход берут консультативную блокировку на пользователя (лимит членств), затем строку группы `FOR UPDATE` (лимит участников); публикация, снятие, выход, удаление участника и копирование берут строку группы и заново проверяют членство под блокировкой, поэтому публикация гонится с удалением участника без «осиротевших» материалов (повторные раунды в тесте). Тесты: 8 одновременных входов в группу на 4 места дают ровно 3 успеха, 7 одновременных созданий при лимите 3 дают 3, снятие против копирования даёт целую копию или 404, 6 параллельных копий получают разные названия.
- **ИИ.** В этой функции моделей нет: ни публикация, ни копирование, ни показ материалов не вызывают ИИ.
- **Минусы.** Код приглашения единственная защита от входа: 10 символов алфавита из 32 знаков (около 50 бит), перебор ограничен общим лимитом запросов, но отдельного ограничителя на подбор кодов нет; при утечке код меняется. Автор виден участникам по имени пользователя (оно же логин). Публикация это снимок: чтобы обновить материал, его снимают и публикуют заново (счётчики и старые копии не связаны). Владелец не может передать группу и не может снять чужой материал без удаления участника.

## 33. Режимы порядка очереди: жеребьёвка и приоритет готовности (нужно подтвердить)

- **Настройки сессии.** `order_mode` (`join` по умолчанию или `lottery`), `ready_priority` (false), `ready_bonus_points` (0..5, 0), `ready_skip_questions` (0 или 1, 0). Задаются при создании (`POST /sessions`) и до закрытия записи меняются через `PUT /sessions/{code}/settings`; после закрытия записи или жеребьёвки 409 `settings_locked`. Все значения по умолчанию дают прежнее поведение, прежние тесты прошли без правок логики (в трёх тестах точного формата ответа добавлены новые поля).
- **Готовность: новое поле, а не `not_ready`.** Поле `entries.not_ready` из п. 28 означает «пропустите меня»: ограничено счётчиком и по умолчанию выключено. «Готов сразу» это приоритет, по умолчанию «ещё готовлюсь» (то есть обычное состояние). Если использовать `not_ready` и для этого, каждый студент по умолчанию тратил бы лимит отметок, а две разные идеи смешались бы в одном флаге. Поэтому добавлено `entries.ready_now`; `not_ready` по-прежнему уходит в самый конец очереди и сочетается с приоритетом.
- **Как хранится порядок.** Порядок вызова по-прежнему определяют `(not_ready, sort_order)`, ничего в запросах очереди не менялось. Студенту «готов сразу» при включённом приоритете сдвигается `sort_order` на `-1 000 000` («полоса готовых»), внутри полосы порядок прежний (по номеру или по жребию). Перенос вперёд (`promote`) ставит выше всех, возврат пропущенного (`requeue`) в конец, как и раньше. Выбор можно менять (`PUT /sessions/{code}/priority`) только пока запись открыта и жеребьёвка не проведена (иначе 409 `ready_locked`); включение и выключение приоритета в настройках пересчитывает полосу. Опоздавший после жеребьёвки не может «обогнать» очередь заявкой о готовности: его выбор игнорируется.
- **Жеребьёвка.** `POST /sessions/{code}/lottery` («Закрыть запись и перемешать») под блокировкой строки сессии и `FOR UPDATE`: закрывает запись, строит перестановку через `random.SystemRandom` (`secrets`-источник операционной системы), перенумеровывает всех записанных числами 1..N и ставит `lottery_at`. Повторный вызов идемпотентен (200, ничего не меняется, в журнал ничего не пишется); гонка шести одновременных вызовов даёт одну жеребьёвку (тест). Чтобы не нарушить ограничения уникальности номеров, текущие номера сначала «паркуются» (сдвиг на константу), потом выставляются итоговые значения одним пакетом. До жеребьёвки вызов (`next`) и перенос вперёд дают 409 `lottery_pending`; студенты в пуле видят «Вы в списке. Порядок определится после закрытия записи» и число записавшихся, номера скрыты (в API `ticket = null`). Опоздавшие (преподаватель снова открыл запись) получают следующие номера по порядку входа, прежние не меняются. Ушедшие и пропущенные до жеребьёвки получают номера после ждущих. Совместимо с «не готов», пропуском, возвратом, переносом вперёд (тесты).
- **Приоритет и жеребьёвка вместе.** Разыгрываются две группы отдельно: сначала «готовы сразу» (номера 1..R), потом остальные (R+1..N); в журнал пишется отдельная запись на каждую группу. Смена готовности во время жеребьёвки: она либо успевает до блокировки и тогда учтена, либо получает 409 (тест на гонку проверяет согласованность номеров и групп).
- **Журнал.** Таблица `session_events` (append-only: тот же триггер запрета `UPDATE`/`DELETE`, что у `audit_log`) без внешних ключей и без имён: `kind = lottery`, группа, число участников, первый номер и итоговая перестановка как список идентификаторов записей. Существующий `audit_log` для этого не подходит: он привязан к сдаче (`submission_id` обязателен). Преподаватель читает журнал на странице очереди («Журнал жеребьёвки», имена подставляются из текущей очереди) и через `GET /sessions/{code}/events-log`. Журнал показывает итог и порядок, но не доказывает случайность: честность опирается на доверие к серверу.
- **Бонус.** `submissions.bonus_points` (по умолчанию 0): при завершении сдачи студенту, который был «готов сразу», присваивается `ready_bonus_points` (только при включённом приоритете). Это отдельное поле: `total_points`, `max_points`, оценки по критериям, история и аналитика не меняются. Бонус виден студенту (`bonus_points` в `/me/submission` и `/me/history`, строка «Бонус за раннюю сдачу»), преподавателю (карточка сдачи и студента) и записан в `audit_log` (`action = bonus`). Преподаватель снимает бонус с причиной (`POST /submissions/{id}/bonus/remove`, пустая причина 422, повторное снятие 409 `no_bonus`, чужая сдача 404), в журнале `action = bonus_remove` с причиной. Штрафов за ложную готовность нет: тест проверяет, что студент, нажавший «готов сразу», а затем «не готов», получает бонус как обычно, оценка не страдает.
- **Пропуск вопроса.** При `ready_skip_questions = 1` готовому студенту выдаётся на один вопрос меньше, но не меньше одного; остальным как раньше. Показывается в настройках сессии и на странице студента.
- **Минусы.** Бонус зависит от флага «готов» на момент завершения (флаг после закрытия записи заморожен, но преподаватель может вернуть пропущенного в конец, полоса при этом теряется, а бонус остаётся). Идентификаторы в журнале жеребьёвки остаются после очистки старых данных, но без имён они ничего не раскрывают. Откат миграции удаляет журнал жеребьёвки и бонусы.

## 34. Бюджет времени и прогноз окончания (нужно подтвердить)

- **Ввод.** При создании сессии необязательно: `duration_minutes` (1..720) или `deadline_at` (с часовым поясом, не раньше чем через минуту и не дальше `BUDGET_MAX_DURATION_MINUTES`, 12 часов); оба сразу 422. Страница преподавателя переводит «до HH:MM» в момент в местном времени браузера (если время уже прошло, берётся завтрашний день). В базе одно поле `queue_sessions.deadline_at`. Без него функция скрыта целиком: `GET /sessions/{code}/budget` отдаёт `enabled = false`, панель на странице не показывается, таймер не меняется.
- **Формулы** (`services/budget.py`, чистая функция `forecast`). Осталось времени `R = max(0, дедлайн − сейчас)`; запас `R * BUDGET_RESERVE_PERCENT / 100` (10%); число оставшихся `N` = ждущие плюс вызванный сейчас; бюджет на студента `(R − запас) / N` (целые секунды, при пустой очереди нет). Прогноз окончания: `сейчас + ждущие * avg_service_seconds + max(0, avg − уже идёт у вызванного)`. Среднее то же, что у времени ожидания студентов (`avg_service_seconds`, сглаженное, стартовое значение `DEFAULT_SERVICE_SECONDS`). Статус: `idle` (никого нет), `ok` (работа укладывается в `R − запас`), `tight` (укладывается в `R`, но запас съеден), `over` (не укладывается или время вышло). Цвета панели: зелёный, жёлтый, красный.
- **Таймер сдачи.** Страница протокола запрашивает бюджет; таймер жёлтый при `≥ бюджета` и красный при `≥ 1,5 бюджета`; ничего не прерывает и не блокирует (e2e проверяет, что «Завершить сдачу» остаётся доступной). Без лимита цвет не меняется.
- **Уменьшение числа вопросов.** Только при статусе `over`, если у сессии подключена работа и вопросов больше одного: предлагается шаг на один вопрос вниз (3→2→1) с прогнозом `сейчас + работа * новое/старое` (предполагается, что время сдачи пропорционально числу вопросов). Состояние не меняется без согласия. Согласие (`POST /sessions/{code}/budget/decision {accept: true, questions: n}`) ставит `queue_sessions.questions_override`; он применяется к следующим вызовам (уже вызванному студенту вопросы не меняются), число вопросов только уменьшается (409 `questions_not_reducible`), работа и банк не трогаются. Отказ запоминает это предложение (`budget_declined`) и больше его не показывает, следующий шаг вниз по-прежнему предлагается. И согласие, и отказ пишутся в журнал сессии (`session_events`, `questions_reduced` и `questions_declined`: прежнее и новое число, оставшиеся студенты, прогноз). Совмещение с п. 33: число вопросов = `min(в работе, override)`, затем минус `ready_skip_questions`, но не меньше одного. Для корректного флага «в банке меньше, чем нужно» в сдаче сохраняется `questions_target` (до этого сдача готового студента с уменьшенным числом вопросов ошибочно помечалась как «короткая»).
- **Студент.** Страница показывает рядом с ожиданием время вызова «≈ 10 мин (около 10:41)»; оно считается на странице из `eta_seconds`, которое сервер пересчитывает при каждом изменении очереди (пропуски, возвраты, завершённые сдачи), поэтому в потоке событий ничего не добавилось и повторных сообщений нет.
- **Права и гонки.** Бюджет и решение доступны только владельцу (чужому 404, без токена 401). Решение берёт блокировку строки сессии: шесть одновременных согласий дают одно изменение и один пункт журнала, решение против завершения сдачи и вызова даёт целые данные (тесты).
- **Минусы.** Среднее время сдачи не знает о смене числа вопросов и подстраивается с задержкой (сглаживание 0,3), поэтому прогноз после уменьшения оптимистичен ровно настолько, насколько верно допущение о пропорциональности. Прогноз не учитывает пропуски и «не готов» в будущем и рассчитан на последовательную сдачу одним преподавателем. Время «до HH:MM» зависит от часов и часового пояса браузера преподавателя; сервер хранит только момент.

## 35. Режимы сессии, единый рабочий экран и QR (нужно подтвердить)

- **Три режима** (`queue_sessions.session_mode`, выбирается при создании, по умолчанию `protocol`, то есть всё как раньше): `queue_only` (только очередь, оценок нет: кнопка «Сдал» завершает запись), `quick` (одна оценка 0..максимум, максимум `quick_max_points` 1..100, по умолчанию 10, плюс необязательная заметка) и `protocol` (критерии и вопросы работы). В двух первых режимах работа с критериями через `PUT /sessions/{code}/assignment` не подключается (409 `mode_no_assignment`).
- **Как хранится быстрая оценка.** Быстрая оценка это обычная сдача с неявным единым критерием «Оценка». Для неё создаётся служебная работа (`assignments.is_system`) «Быстрая оценка (0–N)» с одним критерием и без вопросов; сессия получает на неё `assignment_id`. Благодаря этому без единой правки продолжают работать оценка и завершение сдачи, журнал изменений (`audit_log` пишет балл как `score:<критерий>`), страница и история студента, номера попыток и пересдача, аналитика и слабые места (критерий «Оценка»). Заметка это комментарий сдачи. Служебная работа одна на преподавателя и максимум (создаётся под консультативной блокировкой, гонка восьми одновременных создателей даёт одну работу), поэтому попытки одного студента в разных быстрых сессиях складываются в одну историю. Если у преподавателя уже есть обычная работа с таким же названием, служебной даётся название с пометкой «[служебная]».
- **Служебная работа скрыта и защищена.** Её нет в списке работ и она не учитывается в `MAX_ASSIGNMENTS_PER_TEACHER`; править, удалять, добавлять вопросы и критерии, копировать и публиковать в группу нельзя (409 `system_assignment` или 404). Читать её по идентификатору владелец может (нужно странице оценки), чужой преподаватель получает 404. Существующие данные не меняются: миграция только добавляет столбцы, у всех прежних сессий режим `protocol`.
- **Единый рабочий экран.** Страница `/teacher` теперь содержит очередь, вызванного студента и панель оценки: в режиме `protocol` вопросы, критерии с кнопками баллов, комментарий с быстрыми пометками и завершение; в `quick` один критерий и заметка; в `queue_only` только «Сдал» и «Пропустить». Переходить на страницу протокола для обычной сдачи не нужно; она остаётся для журнала, правок, аналитики и редактирования работ. Панель берёт данные из потока очереди (`assignment_id`, `session_mode`) и не делает лишних запросов, пока никто не вызван.
- **Мастер «Начать занятие».** Одна форма: группа, режим, работа (для `protocol`), время (необязательно), порядок вызова; название необязательно и по умолчанию «Группа, ДД.ММ ЧЧ:ММ» (или «Сдача ДД.ММ ЧЧ:ММ»); поощрения за раннюю сдачу свёрнуты. Значения берутся из последней сессии преподавателя (группа, режим, максимум, порядок, поощрения, длительность как разность срока и начала, подключённая работа) и подставляются, только пока форма не тронута. После нажатия сразу показывается панель с крупным кодом, ссылкой и QR во всю ширину, а кнопка «На проектор» открывает полноэкранный режим с огромным кодом и QR (закрывается Esc или щелчком).
- **QR.** Генерируется на сервере библиотекой `segno` (BSD, чистый Python, без зависимостей, версия закреплена 1.6.6, в запросах наружу не обращается): `GET /api/v1/qr.svg?text=...` (1..300 символов), доступен без входа, возвращает самодостаточный SVG с кэшем на час; страница передаёт в `text` ссылку вида `<адрес>/?code=XXXXXX`. Так как QR кодирует переданный текст, любой может получить QR для произвольной строки: это безвредно, но эндпоинт не следует считать подписью.
- **Цель по кликам** (проверена e2e-тестами). Старт занятия: 1 клик по «Начать занятие» (форма уже заполнена прошлыми настройками). Завершение студента в быстром режиме: 2 действия после вызова (балл, «Завершить»), с клавиатуры от вызова до результата три нажатия: `N`, цифра балла, `Enter`.
- **Минусы.** Прошлые настройки берутся из списка сессий на стороне браузера, поэтому у нового преподавателя форма с настройками по умолчанию. Режим нельзя сменить у уже созданной сессии. Быстрые оценки разных максимумов живут в разных служебных работах, их попытки не объединяются. Проектор и полноэкранный режим зависят от браузера (при отказе остаётся оверлей на всю страницу).

## 36. Быстрый ввод (нужно подтвердить)

- **Список вопросов.** `POST /assignments/{id}/questions/import {text, difficulty, topic, dry_run}`. Каждая строка очищается от нумерации и маркеров (`1.`, `2)`, `(3)`, `4:`, `12 -`, `-`, `•`, `*`, `—`, `а)`; повторяются при вложенности), пробелы и неразрывные пробелы схлопываются, пустые строки пропадают. Распознаётся не всякий префикс: `2024 год…`, `3 примера`, `1.1) …` остаются как есть, а строка «А. Пушкин…» теряет «А.» (известная неточность). Дубли определяются без учёта регистра и внутри вставки, и против уже имеющегося банка. Статусы строк: `ok`, `duplicate`, `too_long` (длиннее 1000), `over_limit` (сверх `MAX_QUESTIONS_PER_ASSIGNMENT`, порядок строк сохраняется). Предпросмотр (`dry_run = true`, по умолчанию) ничего не меняет, страница показывает строки с галочками и счётчиком; «Добавить выбранные» отправляет только отмеченные строки с `dry_run = false`, сервер заново их проверяет и добавляет все `ok` в порядке ввода одной транзакцией под блокировкой работы (параллельные вставки не дают дублей и превышения лимита). Размер вставки до 50 000 символов.
- **Готовые наборы критериев.** Встроенные данные в коде (`services/criteria_presets.py`, не в базе): «Практическая работа», «Курсовая работа», «Устный ответ». `GET /criteria-presets` отдаёт список, `POST /assignments/{id}/criteria/preset {preset}` добавляет критерии, которых ещё нет по названию (без учёта регистра), поэтому повторное нажатие ничего не дублирует; после подстановки критерии правятся обычным способом. Правила прежние: после первой сдачи критерии заблокированы (409 `criteria_locked`), лимит критериев сохраняется (409 `criteria_limit`, пояснение на русском), служебная работа не принимает наборы.
- **Оценка одним касанием.** У каждого критерия кнопки с баллами от 0 до максимума (при максимуме больше 12: 0, половина, максимум; на рабочем экране ещё поле числа), «Всё на максимум», быстрые пометки (фиксированный список: «Отлично», «Хорошо», «Есть ошибки», «Не знает теорию», «Не может объяснить», «Код не запускается», «Нужна пересдача») добавляются в комментарий через «;» и снимаются повторным нажатием, свободный текст пишется рядом. Всё это есть и на рабочем экране `/teacher`, и в форме оценки на странице протокола. Кнопки не меняют серверные правила: проверка диапазона и полноты прежняя.
- **Горячие клавиши** (рабочий экран): `N` следующий студент, `Enter` завершить, цифры ставят балл активному критерию и переводят к следующему (при максимуме 10 и выше двузначное число набирается в пределах 0,7 с), `?` справка, `Esc` закрыть. Клавиши не срабатывают в полях ввода (проверено e2e), выбираются по физической клавише `N`, поэтому работают и при русской раскладке.
- **Студент.** Имя запоминается в браузере в `localStorage` под защитой `try/catch` (e2e с заблокированным хранилищем: страница работает, ошибок нет); если известны код и имя, появляется кнопка «Войти как <имя>», то есть повторный вход в один клик. Таймер сдачи стартует в момент вызова (`started_at` сдачи) и исчезает вместе с панелью при завершении; в завершённой сдаче длительность фиксируется на сервере.
- **Минусы.** Предпросмотр и добавление выполняют разбор дважды (сервер доверяет только повторной проверке). Набор критериев нельзя применить к работе, где уже есть сдачи. Пометки фиксированы в коде, свои не сохраняются.

## 37. Проверка присутствия по меняющемуся коду (нужно подтвердить)

- **Настройка.** `queue_sessions.presence_check`: `off` (по умолчанию, поведение прежнее) или `rotating_code`; `presence_interval` 30..60 секунд (по умолчанию 30). Задаётся при создании сессии и в любой момент меняется владельцем (`PUT /sessions/{code}/presence {mode, interval?}`, для закрытой сессии 409 `session_closed`). Выключение или включение не затрагивает уже вставших в очередь: студент с имеющейся записью повторно входит без кода, проверка касается только создания новой записи.
- **Код.** Шесть цифр, без состояния в базе: `HMAC-SHA256(JWT_SECRET_KEY, "presence:<id сессии>:<номер окна>") mod 10^6`, где окно это `floor(время / интервал)`. Поэтому код одной сессии не подходит к другой и не угадывается без секрета сервера, а смена кода не требует фоновой задачи. Сервер принимает код текущего и предыдущего окна (допуск на задержку не больше одного интервала), код старше, будущий и неправильной формы отвергаются (сравнение за постоянное время; нецифровые и юникодные цифры отвергаются без ошибок). Владелец получает код и число секунд до смены в `GET /sessions/{code}/presence` (`Cache-Control: no-store`); чужой преподаватель 404, без токена 401, студент и публичная информация о сессии видят только режим проверки.
- **Экран и QR.** Страница `/teacher` показывает код крупно («123 456»), обратный отсчёт и QR; код обновляется сам по таймеру на момент смены. QR кодирует ссылку `/?code=XXXXXX&p=NNNNNN` (тот же код как токен), страница студента подставляет его в поле, при сохранённом имени остаётся нажать «Войти как …». QR на панели «Код и QR» и на проекторе обновляются вместе с кодом.
- **Защита от подбора.** Неверные коды считаются в памяти процесса (`services/presence.py`, `AttemptGuard`): `PRESENCE_IP_FAILURES` (5) ошибок за `PRESENCE_FAILURE_WINDOW_SECONDS` (60) с одного адреса в одной сессии блокируют этот адрес на `PRESENCE_LOCK_SECONDS` (120); `PRESENCE_SESSION_FAILURES` (30) ошибок с любых адресов блокируют вход в сессию для всех на то же время. Во время блокировки даже верный код получает 429 `presence_locked` с `Retry-After` и пояснением «Слишком много неверных кодов. Подождите N с и посмотрите на экран». Обычная неверная попытка: 403 `presence_code_invalid` «Неверный код, посмотрите на экран»; пустой код: 403 `presence_code_required` (не считается ошибкой). Проверка выполняется до блокировки строки сессии, поэтому перебор не задерживает остальных. Вдобавок действуют прежние ограничители входа по IP.
- **Тесты.** Допуск предыдущего кода и отказ для старого, граница окна при параллельных входах (часы подменяются), перебор и блокировка по адресу и по сессии, независимость адресов, параллельные неверные попытки (ни одна не проходит, ошибок сервера нет), переключение проверки во время входов, права владельца, совместимость с жеребьёвкой, e2e с экрана преподавателя до входа студента.
- **Минусы** (также в KNOWN_ISSUES): фото кода другу за 30 секунд полностью обходит проверку (код доказывает, что человек видел экран в последние минуты, а не что он в аудитории); счётчик ошибок живёт в памяти одного процесса и сбрасывается при перезапуске, при нескольких процессах лимиты считаются по каждому отдельно; студент за общим NAT с чужим подбором делит блокировку своего адреса; смена `JWT_SECRET_KEY` меняет и коды; расхождение часов сервера и браузера влияет только на отсчёт на экране, а не на проверку.

## 38. Хранение данных, боевая конфигурация и набор для пилота (нужно подтвердить)

- **Срок хранения.** `DATA_RETENTION_DAYS` (по умолчанию 180, `0` отключает). Закрытые сессии (`status = closed`, `closed_at` старше срока) удаляются целиком: записи очереди, сдачи, оценки, показанные вопросы (каскадом, других ссылок на сессию нет). Открытая сессия не удаляется никогда, даже старая (закрыть её может преподаватель или автозакрытие `SESSION_AUTO_CLOSE_HOURS`). Затем удаляются записи студентов, на которые не осталось ни одной записи очереди и которые старше срока: история студента сохраняется, пока у него есть хотя бы одна сохранённая сессия. Это изменение поведения по умолчанию (старые данные пропадают сами), оно вызвано требованием пилота; отключается нулём.
- **Как запускается.** Фоновая задача в приложении (`services/retention.py`, раз в `RETENTION_INTERVAL_SECONDS`, по умолчанию час, первая проверка после первого интервала) и команда `python -m services.retention [--days N] [--apply]`: без `--apply` только считает, с ним удаляет. Удаление идёт пачками по 100 сессий отдельными транзакциями, повторный и параллельный запуск безопасны (удаляется то, что нашлось и не удалено другим; тест на гонку четырёх запусков). Счётчик `queue_sessions_purged_total` в `/metrics` и строка в журнале.
- **Журналы не трогаются.** `audit_log` (оценки и правки) и `session_events` (жеребьёвка, решения по бюджету) устроены как «только дописывать» (триггер запрещает `UPDATE` и `DELETE`) и не имеют внешних ключей, поэтому остаются после удаления сессии. В них нет имён студентов: только идентификаторы, баллы и текст комментариев преподавателя. Я не стал ослаблять триггер ради очистки: целостность журнала важнее, а полезной связи с человеком в нём нет. Минус: комментарии преподавателя остаются бессрочно (об этом сказано в `docs/PILOT.md`); работы с критериями и банком вопросов не удаляются, это материалы преподавателя.
- **Боевая конфигурация** (`docker-compose.prod.yml`, `deploy/Caddyfile`, `.env.prod.example`, `Dockerfile`). Caddy (80 и 443, автоматический HTTPS) перед `web`; `web` и `postgres` без опубликованных портов; пользователь `app` (uid 10001), код только для чтения, корневая ФС только для чтения, `cap_drop: ALL`, `no-new-privileges`; пределы памяти и ротация журналов; postgres с уменьшенными буферами; `AI_ENABLED=false`; `/metrics` снаружи закрыт на уровне Caddy и токеном. `FORWARDED_ALLOW_IPS="*"` допустим только пока `web` не опубликован наружу (сказано в инструкции). Dockerfile стал двухступенчатым (зависимости ставятся в отдельном слое, в образ попадает только виртуальное окружение).
- **Резервные копии.** `deploy/backup.sh`: `pg_dump -Fc`, проверка читаемости `pg_restore --list`, атомарное сохранение (файл `.part` переименовывается), права 600, хранение `BACKUP_KEEP` последних (по умолчанию 14); `deploy/restore.sh` восстанавливает только в новую базу и отказывается писать в `queue_db`. Ротация сначала не сработала (на Windows путь с обратными слэшами ломал `xargs`), цикл на чистом `bash` устранил это; проверено на трёх запусках.
- **Нагрузочные сценарии.** `loadtest/lesson.js` (k6): вход с блокировкой строки сессии, режим жеребьёвки (`ORDER_MODE=lottery`), проверка присутствия (`PRESENCE=1`; студент получает код через токен преподавателя как допущение стенда), быстрая оценка с завершением сдач, просмотр очереди и бюджета; `loadtest/sse_peak.py` принимает `SESSION_OPTIONS` и `PRESENCE=1` для потоков SSE. `loadtest/run.sh` выбирает сценарий переменной `SCRIPT`. **Запуск не выполнялся** (по вашей просьбе остаётся вам на свободной машине): сценарии проверены только на синтаксис, цифр нагрузки нет, выводов о числе студентов на сессию из них не делается.
- **Набор для пилота** (`docs/PILOT.md`): инструкция преподавателю, абзац студентам, анкета из 10 вопросов, метрики и способ их снять, заметка о приватности с реальным сроком хранения и перечнем того, что остаётся.
- **Минусы.** Фоновая очистка работает только в одном процессе (как и остальное в проекте). Удаление необратимо, а резервные копии хранят удалённые данные до своей ротации. Проверка соответствия законодательству не проводилась.

## 39. Описания уровней баллов у критерия (нужно подтвердить)

- **Что.** У критерия необязательный список уровней `{points, text}`: например, 0 «нет ответа», 1 «частично», 2 «верно с неточностями», 3 «верно и полно». Хранится в столбце `levels` (JSONB) таблиц `assignment_criteria` и `space_publication_criteria` (миграция `a4b5c6d7e8f9`). Уровни это подсказка преподавателю: баллы по-прежнему можно ставить любые от 0 до максимума, а оценка студента от наличия уровней не зависит.
- **Ограничения.** До 11 уровней, баллы уникальны и от 0 до `max_points` критерия (иначе 422 `levels_out_of_range`), текст до 200 символов. Уровни сортируются по баллам. Снижение максимума ниже балла какого-либо уровня отклоняется.
- **Редактирование после первой сдачи.** Баллы и максимум блокируются (п. 15), а описания уровней можно менять и после первой сдачи: это пояснение, а не правило оценки. Отдельная ручка `PUT /assignments/{id}/criteria/{cid}/levels`, она же очищает уровни пустым списком. Служебная работа быстрой оценки не меняется.
- **Копии.** Уровни переходят в копию работы, в снимок публикации в предметной группе и обратно в копию у другого преподавателя. Готовые наборы критериев (пресеты) и черновики ИИ уровней не содержат.
- **Где видно.** На экране оценки (`/teacher`) под кнопками баллов список «балл — описание», выбранный уровень выделен, у кнопки подсказка; на `/protocol` те же подписи в форме оценки и правки и редактор «Уровни» (по строке «баллы: описание»). Студент уровни не видит.
- **Минусы.** Описание не привязано к конкретному баллу жёстко: если уровней меньше, чем баллов, у промежуточных баллов подсказки нет. Аналитика уровни не использует.

## 40. Списки групп и вход по списку (нужно подтвердить)

- **Что.** Преподаватель загружает список группы (`PUT /roster`, текст по строке на студента; нумерация и маркеры убираются, повторы по ключу имени пропускаются и перечисляются в ответе, лимиты `MAX_ROSTER_PER_GROUP` 100 и `MAX_ROSTER_GROUPS` 30). Таблица `roster_entries` (миграция `b5c6d7e8f9a0`): преподаватель, ключ и название группы, ключ и написание имени, уникально `(teacher_id, group_key, name_key)`. Новая загрузка заменяет список группы целиком под консультативной блокировкой преподавателя. Группа и имя сравниваются теми же ключами, что и история студентов (п. 29), поэтому записи по списку связываются с историей точно.
- **Вход.** Страница студента показывает кнопки с именами из списка (только тех, кого ещё нет в очереди); студент выбирает себя. Если при создании занятия (или позже в настройках, пока запись открыта) включено `roster_only`, имя вводить нельзя: `join` принимает только имя из списка (иначе 422 `not_in_roster`) и записывает написание из списка; то же имя с другого устройства даёт 409 `name_taken`, повтор с тем же токеном по-прежнему возвращает ту же запись. Включить `roster_only` можно только если у группы сессии есть список (422 `roster_missing`). Без `roster_only` список только подсказка, любое имя принимается как раньше.
- **Цена по скорости.** Проверка по списку добавляет к входу два небольших запроса внутри блокировки сессии, и только при `roster_only`. Для остальных сессий вход не изменился.
- **Публичность.** Имена списка показывает ручка `GET /sessions/{code}/roster` любому, кто знает код сессии (имена тех, кого ещё нет в очереди). Это сознательный компромисс ради выбора из списка; для закрытых сессий и сессий без списка ручка пуста. Фамилии не уходят во внешние сервисы.
- **Минусы.** Тёзки в одном списке различаются только написанием (например, «Иванов И.» и «Иванов Иван» это разные люди, «Иванов Иван» дважды это повтор). Студента, которого нет в списке, преподаватель должен добавить в список или выключить `roster_only`. Импорта из файлов (CSV, Excel) нет, только вставка текста.
