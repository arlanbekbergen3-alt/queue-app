# Нагрузочный тест

Сценарий пика в начале пары: 300 студентов входят в одну сессию за 60 секунд, затем опрашивают позицию, преподаватель вызывает следующего раз в минуту. Всё запущено **локально на ноутбуке разработчика**, это не прод и не оценка для прода.

## Сценарий (`loadtest/peak.js`, k6 0.57.0)

| Участник | Поведение |
|---|---|
| 300 студентов | каждый ждёт случайные 0-60 с, делает `POST /join`, затем 240 с опрашивает `GET /me` с интервалом 5 с + случайные 0-1 с (как `static/index.html`) |
| 1 преподаватель | старт на 15-й секунде; раз в минуту `done` предыдущему и `next`; между ними каждые 3 с `GET /queue` (как `static/teacher.html`) |
| Длительность | 5 минут, ~13 600 запросов |

Критерии прохождения (**мои допущения**, требований от колледжа пока нет): доля ошибок < 1%, p95 `join` < 1 с, p95 `me` < 500 мс, p95 `next`, `done`, `queue` < 1 с.

Модель нагрузки замкнутая (виртуальный студент ждёт ответа), поэтому RPS определяется спросом (около 40-55 запросов/с на пике), а не пределом сервера. Предел сервера смотрит отдельный тест `loadtest/capacity.js`.

## Окружение

- Windows 11 Home, ноутбук, Docker Desktop (WSL2): 8 CPU и 7,6 ГБ памяти доступны Docker.
- Приложение: 1 процесс uvicorn, Python 3.11, PostgreSQL 15-alpine с настройками по умолчанию, оба в контейнерах.
- k6 в контейнере на той же машине (делит с приложением процессор и сеть).
- **Параллельно работали обычные программы пользователя** (браузер, IDE, антивирус). Это главный источник шума, см. ниже.
- Основные замеры идут **внутри сети Docker** (k6 обращается к `http://queue_api:8000`). Через порт хоста (`host.docker.internal`) получены ошибки соединений, которых нет внутри сети; это артефакт локальной среды, и такие прогоны в итоговое сравнение не включены.
- Использование БД: `loadtest/monitor.sh` каждые 2 с читает `pg_stat_activity` и `docker stats`. Значение `db_total` включает простаивающие соединения другого контейнера приложения, если он был запущен (отмечено), поэтому для сравнения надёжнее `active` и `idle in transaction`.

## Версии кода

| | Что внутри |
|---|---|
| **v0** (исходная) | `/me` делает 4 запроса к БД; пул 10 + 20 «переполнения» |
| **v1** (промежуточная) | `/me` делает 1 запрос, но SQL собирается заново на каждый вызов |
| **v2** (итоговая) | тот же 1 запрос, собран один раз при импорте; пул 30 постоянных соединений без «переполнения» |

Поведение API и схема БД не менялись.

## Что происходило (хронология, ничего не скрыто)

1. **Первый прогон v0** (через порт хоста): 4,25% ошибок, p95 3,5 с, p99 40 с, пул соединений заполнен (30 из 30), до 27 соединений в `idle in transaction`, процесс на 100% одного ядра.
2. **Диагностика.** EXPLAIN ANALYZE: запросы выполняются в БД за 0,1-0,6 мс (первый, холодный, 38 мс). БД не узкое место. Профиль CPU (cProfile внутри контейнера под нагрузкой) показал, что время уходит в Python, в разбор и построение запросов SQLAlchemy (36%).
3. **Исправление 1 (v1):** собрать «вид студента» одним запросом вместо четырёх. Профиль v1 показал два новых факта: SQL с `aliased()` собирается заново на каждый запрос, и пул пересоздаёт соединения (70 открытых при лимите 30; каждое стоит SCRAM-рукопожатия, ~410 тыс. вызовов `hmac.digest`).
4. **Исправление 2 (v2):** собирать запрос один раз; пул 30 постоянных соединений.
5. **Шум.** Три прогона одного и того же v2 дали p95 `/me` **1156 мс, 55 мс и 13 мс**. Разница определяется тем, что делает машина в этот момент, а не кодом. Поэтому полные сценарии разных дней сравнивать нельзя; для сравнения использован замер потолка попеременно (ниже) и A-B-A подряд.

## Выводы

1. **При 300 студентах и на тихой машине** (`net-after2`, `ab-before`, `ab-after`) и старая, и новая версии укладываются в мои критерии по p95; ошибок нет. То есть для пилота в одну группу текущая нагрузка не проблема **в тихих условиях**.
2. **Когда машина занята посторонней нагрузкой**, одна и та же версия показывает p95 от 13 мс до 1,2 с (v2) и от 59 мс до 4 с (v0). Требования к задержке на ноутбуке с работающим браузером измерить честно нельзя.
3. **Узкое место, найденное измерением:** процессорное время Python на каждый запрос (разбор и построение SQL в SQLAlchemy), а не БД. Исправление уменьшило CPU на запрос (потолок `/me` +85-90%), число соединений (70 → 30) и хвост задержек (p99 1879 → 28 мс в паре `ab-*`, одна пара, не усредняется).
4. **Перегрузка превращалась в 500.** При избытке запросов запрос ждал соединение из пула 10 с, затем `QueuePool limit ... timed out` и ответ 500 (в логах 295 таких ошибок на пике v1). Потом это заменено на 503 с `Retry-After`, добавлен общий лимит одновременных запросов (`DECISIONS.md`, п. 6). Числа в таблицах выше получены на коде до этих изменений; для нового кода см. раздел «Серии на двух кодовых базах».
5. **Одна сессия.** Все входы идут через блокировку одной строки `queue_sessions`: 300 входов за 60 с (5 в секунду) это выдерживает; при залпе 300 за 5 с входы ждут друг друга (см. серии ниже).

## Серии на двух кодовых базах (10.11, шумная машина)

Различия смешивают несколько изменений сразу (`DECISIONS.md`, п. 12). По 3 повтора, чередование база/новый, каждый прогон на свежей БД и свежем контейнере, всё внутри сети Docker, k6 0.57.0. ### Что изменилось после серий и не измерено

После серий добавлена правка `join` (очередь входов одной сессии в памяти, `join_gate`, и проверка лимита с вставкой одним `INSERT ... SELECT ... WHERE`), чтобы ожидающие блокировку входы не держали соединения пула. **Проверено запуском:** тесты `test_queue_limit_holds_under_concurrent_joins`, `test_joins_of_one_session_wait_in_memory_not_on_database_connections` и `test_insert_entry_if_room_refuses_when_session_is_full` падают, если убрать шлюз или `WHERE`. **Влияние на залп не измерено**: образ `queue_tmp_new:latest` пересобран с правкой, но повторные серии не запускались (владелец запустит сам). Все числа выше получены на коде без этой правки. Значения по умолчанию `MAX_CONCURRENT_REQUESTS=400` и `DB_POOL_TIMEOUT_SECONDS=10` выбраны по одному прогону на вариант (`DECISIONS.md`, п. 6); в какой момент образ получил эти значения относительно начала серий, не записано.

## Что повторить

Цель: сравнить «до» и «после» правки `join` на тихой машине. Условия:

1. Закрыть браузер, игровой клиент, антивирус, IDE и всё, что грузит CPU или память; не пользоваться компьютером во время прогонов. Перед началом записать состояние (загрузка CPU, свободная память, список программ) в `loadtest/results/series/machine-state.txt` с датой.
2. Docker Desktop запущен, стек `queue_db` работает (`docker compose up -d postgres`), в `.env` настоящие значения. Образ нового кода: `docker build -t queue_tmp_new:latest .`. Образ базы `queue_tmp_baseline:step1` уже есть (если удалён, база для сравнения утрачена, сравнивать с сериями выше нельзя).
3. Повторов: минимум 3 на каждый вариант, чередовать ABA.
4. Сценарии: `salvo` и `ssesalvo` (именно в них была проблема); `peak` и `sse` повторять не обязательно.

```bash
cd queue-app

  bash loadtest/one_run.sh salvo base quiet-salvo-base-$n
  bash loadtest/one_run.sh salvo new quiet-salvo-new-$n
```

Метки с префиксом `quiet-` не затирают прежние серии. На что смотреть: p95 `join` и число 503 в залпе, отказы потоков в `ssesalvo`, `idle in transaction` и `active` в `*-system.csv`. После прогонов проверить, что нет остатков: `docker ps -a | grep queue_tmp_` и список баз `queue_tmp_*` в `queue_db` пусты. Образы `queue_tmp_*` удалить, когда сравнение закончено.

## Ограничения

- Это локальный ноутбук с общей нагрузкой, а не сервер. Числа не переносятся на прод.
- k6 и приложение делят один процессор.
- Один прогон на конфигурацию (кроме потолка `/me`, где по два раунда). Доверительных интервалов нет; разброс между идентичными прогонами достигает 20 раз (см. v2).
- Нагрузка по модели замкнутая: преподаватель и студенты не повторяют запросы при ошибке; реальные браузеры повторяют.
- Проверен только один процесс uvicorn. Несколько процессов не измерялись.
- Не измерены: длительная работа (часы), сеть Wi-Fi колледжа, мобильные клиенты.
- Профиль CPU снят под cProfile (замедляет процесс примерно вдвое), годится для долей, не для абсолютных времён.

## Сценарии для новых функций (подготовлены, не запускались)

Новые функции меняют вход и добавляют запросы: вход берёт блокировку строки сессии и проверяет код присутствия, жеребьёвка перенумеровывает всех записанных одной транзакцией, оценки идут через завершение сдачи, преподаватель опрашивает очередь, бюджет и код присутствия. Старые замеры выше этого не покрывают. Для нового кода подготовлено, но **не запущено** (нужна свободная машина, остановленные Ollama и тяжёлые программы, условия те же, что в разделе «Что повторить»):
