# Протокол сдачи: проект расширения

Идея: прозрачные правила сдачи. Оценивает всегда человек. Модель (этапы 3-4) ничего не оценивает и не пишет в оценки.

Статус: этап 1 это проект; реализация по этапам 2-5 описана в `PROGRESS.md`. Всё, что в этом документе названо «решением», принято без владельца и ждёт подтверждения (список в конце).

## a) Модель данных

Все таблицы с первичным ключом `id` (строка UUID, как в остальных таблицах). Время `timestamptz`.

| Таблица | Поля | Ограничения и индексы |
|---|---|---|
| `assignments` (работа) | `teacher_id` (FK `users`, CASCADE), `title` (120), `description` (до 4000, может быть пустым), `questions_per_submission` (1..10, по умолчанию 3), `practice_enabled` (bool, по умолчанию false), `created_at` | индекс по `teacher_id`; `CHECK` на диапазон `questions_per_submission`; уникальность `(teacher_id, title)` |
| `assignment_questions` (банк) | `assignment_id` (FK, CASCADE), `text` (1000), `difficulty` (1..3), `topic` (60, может быть пустым), `position`, `created_at` | индекс по `assignment_id`; `CHECK difficulty BETWEEN 1 AND 3`; уникальность `(assignment_id, text)` (нет дублей) |
| `assignment_criteria` | `assignment_id` (FK, CASCADE), `name` (80), `max_points` (1..100), `position` | уникальность `(assignment_id, name)`; `CHECK max_points BETWEEN 1 AND 100` |
| `queue_sessions` (существует) | **новое поле** `assignment_id` (FK `assignments`, SET NULL, может быть пустым) | индекс по `assignment_id` |
| `submissions` (сдача) | `entry_id` (FK `entries`, CASCADE, **уникально**), `session_id` (FK), `assignment_id` (FK, RESTRICT), `status` (`in_progress` / `completed` / `cancelled`), `started_at`, `ended_at`, `duration_seconds`, `total_points`, `max_points` (снимок суммы максимумов на момент завершения), `comment` (1000), `selection_seed` (hex), `pool_question_ids` (JSONB), `created_at` | `CHECK status IN (...)`; индексы `(session_id, status)`, `(assignment_id, status)` |
| `submission_questions` | `submission_id` (FK, CASCADE), `question_id` (FK, SET NULL), `text`, `difficulty`, `topic` (снимки), `position` | уникальность `(submission_id, position)` и частичная уникальность `(submission_id, question_id)` где `question_id` не пусто (**нет повторов в одной сдаче**) |
| `submission_scores` | `submission_id` (FK, CASCADE), `criterion_id` (FK, RESTRICT), `points` (>= 0), `comment` (300) | уникальность `(submission_id, criterion_id)`; `CHECK points >= 0`; верхняя граница (`points <= max_points`) проверяется в сервисе, `CHECK` между таблицами в БД невозможен |
| `audit_log` (журнал) | `id` (bigint, идентификатор по возрастанию), `occurred_at`, `submission_id`, `actor_id`, `action` (`complete` / `correct` / `reopen`), `field` (`score:<criterion_id>` / `comment`), `old_value`, `new_value`, `reason` | **без внешних ключей** (иначе каскадное удаление родителя упрётся в запрет); индекс `(submission_id, id)`; триггер БД запрещает `UPDATE` и `DELETE`, `reason` не пустой для `correct` (`CHECK`) |
| `ai_jobs` (этап 3) | `teacher_id`, `assignment_id`, `status` (`queued` / `running` / `done` / `error`), `result` (JSONB), `error_code`, `created_at`, `finished_at` | индекс `(teacher_id, created_at)` для лимита в час |

Миграции: одна на таблицы протокола (журнал и триггер в ней), одна на `ai_jobs`. Откат (`downgrade`) удаляет таблицы и триггер; `queue_sessions.assignment_id` удаляется отдельным шагом.

**Критерии и вопросы после первой сдачи (решение).** Критерии после первой сдачи **блокируются**: добавление, правка и удаление дают 409 `criteria_locked` с понятным текстом. Альтернатива (версионирование критериев) сложнее и меняет смысл старых оценок. Вопросы можно править и удалять всегда: сдача хранит **снимок** текста вопроса, старые сдачи не меняются. Работу с хотя бы одной сдачей удалить нельзя (409 `assignment_has_submissions`).

**Журнал.** До завершения оценки сохраняются как черновик без журнала. Журнал пишет: завершение (`complete`, все итоговые оценки), любую правку после завершения (`correct`: было, стало, причина обязательна), повторное открытие пропущенного студента (`reopen`). Неизменяемость обеспечивает триггер БД, а не код приложения; тест проверяет, что прямой `UPDATE` и `DELETE` падают. Ограничение: владелец БД или суперпользователь может отключить триггер. Журнал защищает от ошибок и правок через приложение, а не от администратора базы (предположение о модели угроз).

## b) Права доступа

- Преподаватель видит только свои работы, вопросы, критерии, сессии, сдачи и журнал. Чужие объекты дают **404** `*_not_found` (не 403), чтобы не раскрывать существование. Проверка владельца идёт запросом с условием по `teacher_id` (работа) или через сессию (сдача), а не отдельной проверкой после загрузки.
- Студент без аккаунта: по коду сессии и `X-Entry-Token` (хеш токена, как сейчас) видит только **свою** сдачу: после завершения вопросы и разбивку баллов, до завершения только статус. Эндпоинт один: `GET /sessions/{code}/me/submission`; идентификатор сдачи в пути не принимается, подбирать нечего.
- Идентификаторы это UUID v4, но защита не на них: каждый запрос проверяет владельца.
- Тренировка (этап 4) доступна по коду сессии и только если преподаватель включил `practice_enabled` (см. риски: банк виден всем, у кого есть код).

## c) Случайный выбор вопросов

- При вызове следующего студента (`next`), в той же транзакции под блокировкой сессии, создаётся сдача.
- Выбор: `selection_seed` = 128 бит из `secrets`, пул = вопросы работы, отсортированные по `(position, id)`, выбор `random.Random(seed).sample(pool, n)`, где `n = min(N, размер пула)`. Без повторов в сдаче (`sample` без возвращения, плюс уникальный индекс).
- Воспроизводимость для аудита: хранятся `selection_seed`, `pool_question_ids` и выбранные вопросы со снимками текста. По `seed` и `pool_question_ids` выбор повторяется, преподаватель видит их в карточке сдачи. Студенту `seed` не показывается.
- Защита от подбора: `seed` секретный и нигде не отдаётся студенту; выбранные вопросы студент видит только после завершения; пропущенного студента, которого вернули в очередь, снова вызывают с **теми же** вопросами (нельзя пересдать «до удобного билета»).
- Если вопросов в банке меньше `N`, выбираются все, в карточке пометка. Баланс по сложности не делается (предположение: достаточно случайности; сложность видна в записи).

## d) API и экраны

Префикс `/api/v1`. Все ответы об ошибках в существующем формате `{detail, code, request_id}`; ошибки валидации с полем и причиной (`errors` с `loc`, `type`, `ctx`), страница показывает русский текст.

Преподаватель (Bearer):
- `POST/GET /assignments`, `GET/PATCH/DELETE /assignments/{id}`
- `POST/GET /assignments/{id}/questions`, `PATCH/DELETE /assignments/{id}/questions/{qid}`
- `POST/GET /assignments/{id}/criteria`, `PATCH/DELETE /assignments/{id}/criteria/{cid}`
- `PUT /sessions/{code}/assignment` (`{assignment_id}` или `null`; нельзя менять, если в сессии уже есть сдачи)
- `GET /sessions/{code}/submissions`, `GET /sessions/{code}/submissions/current`
- `GET /submissions/{id}`, `PUT /submissions/{id}/grades` (черновик), `POST /submissions/{id}/complete`, `POST /submissions/{id}/correct` (`reason` обязателен), `GET /submissions/{id}/audit`
- этап 3: `POST /assignments/{id}/ai/draft`, `GET /ai/jobs/{id}`, `POST /ai/jobs/{id}/approve`
- этап 5: `GET /assignments/{id}/analytics`, `GET /sessions/{code}/analytics`

Студент (код + токен записи): `GET /sessions/{code}/me/submission`.
Тренировка (этап 4, по коду сессии): `GET /practice/{code}`, `POST /practice/{code}/check`, `GET /practice/{code}/jobs/{job_id}`.

Совместимость: существующие эндпоинты и их ответы не меняются. Единственное изменение поведения касается **только сессий с подключённой работой**: `POST /entries/{id}/done` при открытой сдаче возвращает 409 `submission_open` (завершение через `complete`, который закрывает и запись); пропуск (`skip`) отменяет открытую сдачу (`cancelled`). Сессии без работы работают как раньше.

Экраны:
- `/teacher`: панель «Работы» (создание, вопросы, критерии, привязка к сессии, черновик модели), карточка текущей сдачи (таймер как подсказка, вопросы, поля баллов, комментарий, «Завершить сдачу»), список завершённых с правкой (причина обязательна) и журналом, аналитика.
- `/`: после завершения сдачи студент видит вопросы и разбивку баллов; ссылка «Тренировка», если включена.
- `/practice`: отдельная страница тренировки (этап 4), с пометкой «тренировка, не официальная оценка».

## e) ИИ-часть и аналитика

Что уходит наружу из процесса: **только текст работы** (этап 3) и **вопрос с ответом студента** (этап 4, не сохраняется). Не уходят: имена, талоны, оценки, идентификаторы. Модель локальная (Ollama на этой же машине или в сети владельца), провайдер за интерфейсом и заменяется настройкой.

Чего не делаем (намеренно): оценку работы студента моделью, влияние тренировки на оценки, показ преподавателю результатов тренировки по именам, хранение ответов студентов в тренировке, автоматическое утверждение черновика модели, Telegram-уведомления.

Аналитика (этап 5) без модели: агрегаты по работе и по паре «работа + сессия», выбросы по длительности относительно медианы своей группы результата, текст по шаблону, только номер талона, порог минимальной выборки в настройках.

Слабые места (расширение аналитики): в тот же ответ `GET /sessions/{code}/analytics` и `GET /assignments/{id}/analytics` добавлены `weak_spots`, `first_attempts` и `retakes`. Для каждого критерия считаются средний процент от максимума и доля сдач ниже 50% (ровно половина баллов не считается провалом), выделяются три самых слабых критерия, вопросы с самым низким итогом сдач (вопрос показывается, если выпадал не меньше минимума раз; отдельных баллов за вопрос нет, оценивается итог сдач, в которых он выпал) и распределение итоговых результатов по десяти корзинам по 10%. Порог 5 сдач действует отдельно для каждой выборки: первые попытки и пересдачи считаются раздельно, пересдач меньше порога дают только пояснение. Имён и талонов в этих блоках нет. Таблицы и полосы показываются на странице `/protocol`.

Копирование и шаблоны: `POST /assignments/{id}/copy` и `POST /assignment-templates/{id}/create` создают независимую работу с теми же критериями и банком вопросов (без сдач, баллов и журнала); флаг `is_template` отмечает работу как шаблон, `GET /assignment-templates` показывает шаблоны преподавателя. Управление на странице `/protocol`.

Общий банк предметной группы: преподаватели одного предмета создают группу (код приглашения у владельца), публикуют снимки критериев и банка вопросов и копируют чужие материалы в свои работы с указанием автора и группы. Студенты, баллы, сдачи, журнал и аналитика в группу не попадают и ей не видны. Подробности и ограничения в docs/DECISIONS.md, п. 32. Страница `/spaces`.

Режимы порядка очереди: при жеребьёвке студенты входят в общий пул без номеров, преподаватель одним действием закрывает запись и перемешивает очередь, перестановка пишется в append-only журнал `session_events`. Приоритет готовности даёт бонус отдельной строкой (`submissions.bonus_points`, не в баллах по критериям, снимается с причиной через `audit_log`) и необязательное уменьшение числа вопросов. Подробности: docs/DECISIONS.md, п. 33.

Бюджет времени: при заданном времени на сдачу у преподавателя панель с остатком, бюджетом на студента и прогнозом окончания; при «не успеваем» предлагается уменьшить число вопросов на сессию на один с явным согласием, решение пишется в `session_events`. Подробности: docs/DECISIONS.md, п. 34.

Режимы сессии и рабочий экран: быстрая оценка хранится как обычная сдача с неявным единым критерием служебной работы, поэтому журнал, история и аналитика работают без изменений; панель оценки встроена в страницу очереди. Подробности: docs/DECISIONS.md, п. 35.

Быстрый ввод: вставка списка вопросов с предпросмотром, встроенные наборы критериев, оценка кнопками, горячие клавиши и повторный вход студента в один клик. Подробности: docs/DECISIONS.md, п. 36.

Проверка присутствия (необязательная): на экране преподавателя меняющийся шестизначный код и QR с тем же кодом, сервер принимает текущий и предыдущий, подбор ограничен по адресу и по сессии. Подробности и честные ограничения: docs/DECISIONS.md, п. 37.

## f) Объём, риски, допущения

Этапы: 2 (протокол), 3 (черновик банка моделью), 4 (тренировка), 5 (аналитика), 6 (документация, проверка).

Риски:
- **Приватность оценок.** Оценки это персональные данные; студент видит только свои; журнал содержит оценки. Хранение в БД открытым текстом, шифрования нет. Резервные копии содержат оценки (см. `DEPLOY.md`).
- **Принятие преподавателями.** Журнал и аналитика могут восприниматься как контроль. Поэтому аналитика анонимна (талон), а выбросы формулируются как «стоит посмотреть», не как вывод.
- **Тренировка раскрывает банк.** Всё, что в банке, видно студенту при включённой тренировке, а случайный выбор теряет смысл. Решение: тренировка выключена по умолчанию и включается преподавателем явно; для настоящей сдачи использовать отдельные вопросы.
- **Скорость модели на CPU** не измерена; качество русского языка не проверено (предположение, что qwen3.5:9b достаточно).
- **Prompt injection** в ответе студента: смягчается, но не исключается (см. `LEARNING.md`); поэтому вывод модели ни на что не влияет, кроме текста подсказки студенту.

Допущения (не проверены): группа до 300 человек, один процесс, одна модель одновременно, вопросов в банке десятки, а не тысячи, преподаватель согласен проверять черновик модели вручную.

## Что нужно подтвердить владельцу

1. Критерии блокируются после первой сдачи (вместо версионирования); вопросы правятся свободно благодаря снимкам.
2. Журнал: триггер БД запрещает `UPDATE` и `DELETE`; черновики до завершения не журналируются; администратор БД всё равно может обойти.
3. Работа привязывается к сессии, а не к записи; одна работа на сессию.
4. Завершение сдачи через `complete` закрывает и запись; `done` при открытой сдаче 409 (только для сессий с работой).
5. Пропущенного студента вызывают с теми же вопросами.
6. По умолчанию 3 вопроса, максимум 10; критериев до 20, вопросов в банке до 200, работ на преподавателя до 50 (значения не обоснованы измерением).
7. Тренировка по умолчанию выключена и раскрывает банк вопросов.
8. Порог аналитики (минимум сдач) и коэффициент выброса по умолчанию (значения в разделе этапа 5).
9. Модель `qwen3.5:9b` взята из задания: что она существует в Ollama и работает по-русски, я не проверял.
